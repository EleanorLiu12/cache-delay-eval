Effects of prefix-cache reuse and queue depth on time to first token

Kejun Liu

CS 699 research project · Qwen3-0.6B on vLLM-Metal, Apple M3 Pro

Week 1–2 calibration study · Status: complete and independently validated

Abstract. A controlled vLLM-Metal experiment measuring prompt length, cached-prefix length, and queue depth. The resulting lookup table supplies empirical latency estimates for the next-stage distributed routing emulator. Reusing a 512-token cached prefix saved 102.5 ms at idle, but at queue depth 2 the same cached path took 1157.1 ms, 4.8× the 240.1 ms time to first token of an uncached, idle replica. Cache locality is therefore not a binary routing preference.

1Queueing delay can exceed the latency benefit of prefix reuse

For a 1024-token prompt, reusing 512 cached tokens saved 102.5 ms at idle. At queue depth 2, that cached path took 1157.1 ms, 4.8× the 240.1 ms time to first token (TTFT) of an uncached, idle replica. Figure 1 shows the full response surface across all 27 valid combinations of prompt length, cache reuse, and observed queue depth.

2Idle cache reuse provides a measurable latency budget

At idle, prefix reuse is worth a bounded and measurable amount of prefill time. Figure 2 reports the absolute and relative saving for each prompt length and queue depth; Table 2 lists the three quantities that constrain the routing decision.

Table 2. Quantities bounding the routing decision, from the 1024-token prompt conditions.

3Routing should compare cache benefit against queueing cost

Cache locality should not be treated as a binary preference. A router should choose the cache-holding replica only when its additional queueing cost is smaller than the prefill time expected to be saved by reuse.

3.1The experiment supplies an empirical cost model

The lookup turns prompt length, cached-prefix length, and queue depth into an expected TTFT. The routing decision can therefore compare predicted latency instead of choosing a server from cache hits alone.

3.2The measured boundary is system-specific

These values describe Qwen3-0.6B on vLLM-Metal and an Apple M3 Pro. This is a single-server calibration, not evidence yet about stale state or multi-replica routing behavior.

3.3Refine the boundary, then test routing policies

Queue depths 0, 2, and 8 show that the decision reverses before depth 2, but do not locate the exact crossover. Depth 1 is the next calibration point before the lookup is used in the two-replica emulator.

4Independent validation stays close to calibration

A separately randomized five-trial run tested all 27 conditions with corrected suffix nonces and no audit failures. Observed values track the calibration expectations within a few percent (Figure 3, Table 3).

5Calibration protocol and quality controls

  1. Exact prompts. Token IDs fix prompt and block-aligned prefix lengths exactly for the server tokenizer.
  2. Observed queues. Each probe begins only after server metrics confirm the requested running-plus-waiting depth.
  3. Manipulation checks. Every accepted row matches its target prompt length, cache-hit tokens, and queue depth.
  4. Safe continuation. Interrupted runs resume only after existing rows, configuration, and schedule identity are validated.

Failed and system-contaminated attempts were excluded, not erased. An early validation run revealed 32 unintended shared tokens, and later attempts encountered a desktop-wide latency shift under high GPU load. Those runs remain preserved locally for auditability but do not contribute to the published lookup, figures, or reported validation errors.
